# Loom Development Constraints

Loom is a personal Web application centered on Checklist. The API is a formal product interface, and the future CLI will use the same API. Before implementation, read the [design document](docs/design.md), [UI Design](docs/ui-design.md), and [roadmap and milestones](docs/roadmap.md). Documents describe the target design, not completed functionality.

## Technology and Scope

- Use pnpm 12.4.1 consistently, pinned by packageManager. Commit pnpm-lock.yaml and use `pnpm install --frozen-lockfile` for verification/deployment. Do not maintain package-lock.json.
- Use TypeScript, Fastify, React/Vite, and SQLite; one service provides Web static assets and the `/api/v1` API.
- v1 targets a single user and must work on desktop and mobile. Start with a light theme, visually referencing the simple Memos layout.
- SQLite is the primary store; historical snapshots may use versioned JSON inside the database. JSON/YAML files are not the primary database.
- The server must enforce all business constraints; Web and the future CLI must not bypass them. Validate input at runtime, and keep database migrations traceable.
- Keep implementation simple, prioritizing existing code and dependencies. Do not prematurely implement collaboration, offline synchronization, scheduled generation, or a CLI client.

## Product Invariants

- Core concepts are Item, Category, Template, and Checklist. Item is a shared identity. Category is centrally managed, does not allow hierarchy, and an Item can belong to multiple peer Categories.
- Template and Checklist share entry editing behavior: Select from the Item list or Category, add entire categories, use temporary entries, notes, and sorting. Do not display or edit quantity/unit in the Web for now (they occupy space and are currently unnecessary); retain these fields in data and API, preserve their old values on merge/update, and do not migrate.
- Temporary entries have no Item reference, can be used independently, and can be converted into Items. Do not automatically merge solely by matching names.
- Checklist is an independent instance of a Template and can also be copied from a Checklist. Checked states belong only to the current Checklist and are not written to Item, Category, or Template.
- Current Template editing pages and active Checklists show the latest Item names; archives show name snapshots at save time. Restoration/copying uses the latest names of surviving Items, without name-change warnings.
- All Item additions to Template and Checklist automatically merge only by Item ID, with no Keep both option. Each nonempty Item ID has only one entry per document. Retain existing quantity, unit, notes, order, and checked state; do not automatically sum quantities. Do not merge temporary entries by name.
- Items are editable and can be deleted only when the effective reference count is zero. Category memberships, current Template entries, and active Checklist entries count as references; archive snapshots do not. The deletion check and deletion must share a transaction, with database constraints preventing dangling references.
- Snapshots must remain queryable after historical Items are deleted. On restore, copy, or conversion to template, retain missing Items as temporary entries by default, without losing content, automatically creating Items, or linking by matching names. The API still permits explicit linking/creation.
- An archived Checklist is read-only and can be queried, restored, copied, or converted to a Template. Copying resets checked states; conversion to a template omits checked states. Restoring the original checklist retains its checked states. An active or archived Checklist can be permanently deleted after confirmation in the settings Modal (`DELETE /checklists/:id {version,confirm:true}`), including its entries, sections, and archive snapshot, releasing Item references without affecting templates or other checklists. Do not substitute archiving for deletion.
- Require explicit confirmation before deleting a Template. Source information and snapshots of existing Checklists remain queryable.

- Checklist has an optional use date `useDate` (YYYY-MM-DD or null), with no time/timezone; Template has no date. Archive/restore preserve the date. Confirmation dialogs for manual creation, copying, and template instantiation all offer an optional "Execution date" (defaulting to the selected calendar day, otherwise unscheduled). The calendar filters checklists of all statuses by date, and date dots include archived records.
- Clicking Checklist navigation must clear the date filter and show all checklists; only clicking a calendar day filters to that day. Show the filter date as small Page status text to the right of the title (not enlarged into a heading), without a separate line above the list. Creating a Checklist with a selected date defaults to that date. Date editing autosaves and obeys structural version and safe-retry rules.

## Implementation Defaults

The following defaults were chosen to implement the design. To adjust them, update the design documents first, then change the implementation.

- All Categories are peers; parentId, child categories, and recursive membership are unsupported. Adding an entire category includes only its direct members.
- Mutable resources use version numbers for optimistic concurrency control. Stale edits return conflicts rather than silently overwriting. Checking does not validate structural version, and the last submission wins; structural editing does not write back checked.
- Resource IDs use UUIDs and are never reused.
- Template and Checklist autosave, replacing current content in a transaction without version history, and show save status and failure retries. One-time actions such as dragging, removal, and addition save immediately; only text input waits for a 500ms pause. During structural saves, entries already on the server remain checkable; only unsaved new entries are temporarily uncheckable.
- Archiving deletes active entry rows to release references. Restoration rebuilds from the snapshot and deletes the archive snapshot.
- Creation, instantiation, copying, conversion to template, template saving, historical restore, and checking use persistent requestId deduplication. Request results and business writes share a transaction; retries return the original result, the same ID with different content returns a conflict, and v1 does not automatically expire records.
- The default single account is set up on the first Web visit (CLI initialization is optional). Web uses secure sessions; external API access uses revocable tokens. Global data/loom.config.json auth.enabled=false can explicitly disable Web/API authentication, including LAN devices. Anonymous writes still validate CSRF and Origin (if supplied). Valid Bearer tokens remain usable; supplied invalid tokens still return 401.
- Delete a Category only when it has no members or active category-group references; historical snapshots do not block deletion.

- A Category can open its own Item member list, deduplicated by Item ID; do not show parent/child category navigation. Removal only unlinks the specified category relationship, preserving the Item and its other category relationships. Details reuse Page/AppLayout and the Item editing dialog.

## Web UI and Component Constraints

- AppLayout shares a bottom account bar: When signed in, show the server-provided username, user icon, and vertical more menu; place sign-out in the account menu. Escape closes the menu and restores focus. Authentication-disabled mode shows a distinct indicator without a username or sign-out. On mobile, authentication-disabled mode keeps only the four navigation entries; authenticated mode retains the account-menu entry.

- Checklist/Template/Item/Category navigation uses the shared AppLayout NavigationLink with real href and aria-current, not Button. Ordinary clicks use the existing leave guard; modifier keys, middle clicks, and copying links retain native browser behavior. Desktop uses the system sans-serif font measured in Memos, 13px/18px, weight 400, 28px line height, 8px horizontal padding, and 16px line icons. Mobile retains touch targets of at least 44px.

- All buttons use Button from `web/button.tsx`, sharing five styles: primary, ordinary, dangerous, lightweight, and icon. Form submissions explicitly use `type="submit"`. Business pages set only layout and dimensions, without overriding base borders, backgrounds, hover, or disabled styles. Ordinary actions such as "Reload" retain visible borders; dangerous actions such as deletion use dangerous styling rather than ordinary text.

- Template/Checklist "New section" appears directly in the shared Page top action area, not inside the Add entry dialog. Add entry offers an exclusive "Add from Item / Add from Category" segmented toggle (reuse view-switch), sharing one pinyin search box, with click-to-add. Category rows offer "Select one" and "Add entire category". Place temporary entries in the bottom action area. The list area has a fixed height; switching sources preserves dialog size and position. Keep the dialog on failure and provide cancellation.

- Reference Memos fonts, sizes, proportions, and compact hierarchy, starting with a light theme. Retain warm gray backgrounds, white cards, and green accents. Do not change the palette without user request; proportion adjustments must not sneak in theme changes.
- All four pages must share AppLayout (sidebar, calendar, mobile navigation, right-side container) and Page (title, create button) from `web/layout.tsx`. Page centrally renders top view icons and the primary action; pages pass only `primaryAction` label/onClick, without injecting custom button-layout JSX. Do not implement individual headers or position buttons per page. Create buttons on all four list pages must have aligned top/right edges; they may be hidden in detail editing.
- Item/Category share the catalog editing structure, and Checklist/Template share the Documents editor. Separate shared layout from business editors; different domains do not have to use identical fields.
- Center the right-side area outside the sidebar, with a maximum width of 960px and adaptation to narrow screens. Keep font sizes, weights, spacing, and control heights consistent. Retain mobile touch targets; do not sacrifice usability to reduce proportions.
- The desktop sidebar shares a calendar; mobile provides a collapsible calendar using the same Calendar component. Navigation clicks obey unsaved-change prompts and do not bypass leave protection.
- Ordinary business input/textarea fields use `data-1p-ignore="true"` and `autoComplete="off"`. Login fields retain username/current-password autofill; do not disable password managers on the login page.
- Dialogs share Modal, focusing the first control on opening and restoring focus to the trigger after Escape or backdrop click closes them (same onClose; no Escape on mobile). Close the native dialog before removing its DOM. Keyboard focus must be clearly visible.
- All confirmation prompts (delete, discard changes, leave protection) use `ask()` from `web/modal.tsx` (Promise<boolean>, Modal + shared Button, dangerous actions use dangerous styling and name the action). `window.confirm/alert/prompt` are prohibited. Leave guard `leave.guard` may return a Promise. Browser Back first stays on the original page, then replays the same step after confirmation.

- Collections of all four resource types and Category members share Collection/RecordCard from web/collection.tsx, supporting card and list views. Page centrally provides the toggle; the choice is shared across all four pages and stored locally in the browser. Clicking a card/list row opens it, with keyboard support and no separate "Open" button. Internal edit/delete/remove actions do not trigger opening. Switching card/list views changes only the content collection, not Page or header width, position, background, border, or padding; do not rewrite the page shell based on content view. Lists organize rows in one white panel with fine dividers. RecordCard shares left record-main and right record-actions areas. Card views show descriptions below names; list rows use a single line with columns (name + information), without notes or wrapping, and do not spread descriptions and large buttons horizontally. Edit/delete use compact icon actions with accessible names. Category member addition uses a header action and Modal, avoiding multiple rows of persistent form toolbars.

### Style System

- Shared Button default text uses 13px/18px (`--font-sm`), independent of body or input font sizes. Retain 28px desktop button height and at least 44px on touch devices.

- Maintain `web/style.css` in component sections, defining each selector once. Modify original rules in place rather than appending overrides at the end.
- Font sizes, spacing, radii, control heights, and colors use `:root` variables, not scattered literals. Font sizes have only four tiers: 12/13/14/18 (`--font-xs/sm/md/lg`). Spacing: 4/8/12/16/24. Radii: 6 (controls/tags)/8 (cards)/10 (panels/dialogs).
- Buttons, inputs, search boxes, and view toggles in the same row uniformly use `--control-h` (28px), with `--touch-h` (44px) for touch (`pointer: coarse`). Calendar cells are an exception and retain a compact grid.
- All UI icons use the `lucide-react` library. Business pages prioritize `Icon` from `web/layout.tsx`, explicitly importing only needed icons. Do not draw SVGs, handwrite paths, copy icon paths, or embed handwritten SVGs in CSS. Do not use text characters such as ‹ › ⋯ × as icons. Library-generated SVGs are allowed. Sizes, stroke widths, and colors follow shared styles; icon buttons retain aria-label/title, and branding uses existing PNG assets.
- Use only one narrow-screen breakpoint, `max-width: 650px`, with 16px mobile horizontal gutters (`--gutter`). Update this section before adding breakpoints.
- Mobile card views use two equal-width columns and truncate long names; list views remain single-column.
- Mobile card metadata shows the Group icon/name plus one category tag on one line (single category name or "N categories" for multiple categories). Truncate long Group names, prioritizing the category tag. Desktop continues to show specific categories.
- Mobile card-corner icon buttons are tightened to 28px wide and 44px high on touch, with no gap between buttons, as requested. This is a local exception to the 44px touch-width rule.
- Page card/list view toggles are fixed at 28px per button and a 28px outer height, without enlargement on mobile. Source toggles in addition dialogs still retain 44px touch targets.
- Mobile control sizes apply directly under narrow-screen or coarse-pointer conditions, without waiting for touch detection, preventing size jumps on refresh. Retain the local dimension exceptions above.
- List rows, Documents entries/sections, and Category members share white panels with fine dividers. Editable entry inputs use a light fill to indicate editability, showing borders on hover/focus; read-only fields have no fill and resemble ordinary text. Prefer shared Icon buttons for inline actions. Ordinary text actions use shared Button; do not remove button borders per page. Entry notes are not persistent inputs: An edit icon opens a Modal, and existing notes appear in 12px on a second line below the name. Do not show source counts. Removal uses an X icon. Do not provide move-up/down buttons. Entries and sections share ordering under the same parent (sections record their preceding sibling entry in afterEntryId; null means first, omission means after sibling entries, existing data needs no migration; new entries appear at the end of their parent). Dragging any row before/after any other row makes it a sibling (allowing hierarchy changes, promoting old levels to siblings). Dropping on the lower half of a section heading makes it the first child content (highlight the target and expand automatically). Sections can be dragged into first-level sections; reject more than two levels. Items can be dragged into sections. After focusing a row, arrow keys move entries across sections in visible order and sections among siblings. The entire row (including disabled fields such as read-only names) can start dragging; hovering the whole row shows a light background and grab cursor. Only editable inputs and buttons do not trigger dragging. Indent the notes second line slightly. Checklist check controls are circular. Mobile entries are single-line: name and actions share one line; hide entry Item tags and notes to make room for names. Desktop Item entry name/description/tags areas fill remaining width, trailing controls have fixed widths, and columns align across rows. Disabled inline icons retain their space (visibility: hidden); do not disrupt alignment with display: none. Tags do not wrap; truncate overflow with ellipses. Within entries, show only Group plus one category tag; combine multiple categories as "N categories", with full names in title.
- Settings Modals place fields above (inputs and related buttons aligned on one row) and actions below a divider using shared Button. Ordinary actions retain visible borders, and dangerous actions use dangerous styling; do not override them as borderless text lists.
- Page `status` displays short states such as Saving/Saved to the right of the title (12px, gray, truncatable, shrinking before the title). Do not insert paragraphs above content that shift the layout downward. Errors remain fully displayed at the top of content with `role="alert"`.
- Mobile headers do not wrap: Truncate titles to one line. When secondary actions are also present, show only the primary-action icon while preserving its accessible name.
- All dragging uses SortableRow from `web/sortable.tsx`; pages must not separately implement pointer/touch dragging. While dragging, the original row fades, a row copy follows the pointer, targets show an insertion line (drop-before/after) or drop-inside highlight (drop-hover), and page text selection is disabled.
- Dropdown selection uniformly uses Select from `web/select.tsx`, not native `<select>` or custom dropdown implementations. Typing filters, supporting full pinyin/initials (`pinyin-pro`, e.g. jid matches the Chinese word for eggs, pronounced jidan). Arrow keys and Enter select, and Escape only closes the list. Select all text on focus only on non-touch devices (doing so on touch displays the system copy/paste menu). `allowCustom` allows free-form values such as Group. Field titles use an outer `<label>` like other inputs and share global label styling (`label > .combobox` has the same spacing as inputs), without separate field-title styles. The position: fixed option list follows the input (updated on scroll/zoom) and must not be clipped by Modal scrolling. Page search shares the same `matchesText` function.
- Clicking or touching outside the shared Select (including blank dialog areas) must close its dropdown and clear filter text, rather than relying only on input blur. Reuse useOutsideClose without blocking the target click or stealing focus; retain internal option clicks and layered Escape closing.
- Do not override component styles with broad element selectors such as `article button`; attach styles to component classes.

- Record each milestone status and acceptance evidence in the roadmap. Clearly mark anything incomplete or unverified.

- Category members show a single-line name, without persistent notes/direct-member descriptions or check circles. Membership and removal appear directly as category tags on the right. Remove the "Back to categories / Member count" bar, retaining Add member at the top. Support direct entry dragging and keyboard up/down sorting; order belongs only to the current Category, is saved in the database, and is protected by version/requestId. Card edit/delete actions are in the top-right corner; changing content must not alter the page header.

- Template/Checklist creation shares a Documents + Modal form; browser prompt is prohibited. Share name input, create/cancel, errors, and retries of the original request.

Template view mode directly offers "Create checklist" in the header (wait for autosave to finish, then copy current content). Put name/date and dangerous actions in a shared Modal, and entry-source selection in the Add Modal. Retain save status, retry, and read-only protection; do not remove features to clean up the interface.

- Show Item categories as tags, not separate body paragraphs. Card notes use 12px, uniformly reserve two lines, and truncate long notes; reserve the space even when there are no notes. Titles are limited to one line and cards have equal heights. Show at most two category tags plus the remaining count; full names are available through title/Item editing. Keep edit/delete at the top right.

- Creation dialogs for all four resource types share ResourceDialog from web/resource-dialog.tsx (title, name, errors, fields, submit/cancel); catalog editing reuses the same form. Pages pass only business fields, state, and save callbacks, without duplicating dialog-form scaffolding. All use Modal underneath, retaining failure retries and focus semantics.

- Web URL routing is centrally managed by web/router.ts: /items, /categories, /templates, /checklists, with resource IDs appended for details and ?date=YYYY-MM-DD for calendar filtering. The root path defaults to /items in authenticated mode and /checklists in authentication-disabled mode. Refresh, direct navigation, and forward/back must retain resource location; browser-history navigation also obeys unsaved-change protection. The server provides SPA fallback only for Web routes; unknown API routes remain JSON 404 responses.
- Session initialization must not display a login-like waiting page. The initial HTML uses the warm gray background; show content after session checking and catalog loading. If no account exists, the server session returns setupRequired:true and the login form is reused to set up the account. For existing accounts, show the login form only for session 401 responses; other errors offer retry. Do not bypass server validation using locally cached authentication flags.

- Category member sorting has no handle: Drag cards/list rows directly. Mouse movement must exceed a threshold to count as dragging; mobile dragging starts after a long press, while ordinary swipes still scroll. Retain arrow-key sorting. Dragging does not open records, and internal actions do not start dragging. Persist sorting through the existing version and requestId API.

- Item names uniformly use 13px/500 in the shared ItemSummary (catalog, Category members, mobile Template/Checklist entries, and temporary-entry name inputs), smaller than first-level section headings; do not override this per page. Exception: Desktop (>=651px) Template/Checklist entry names use 14px/400 (`--font-md`), following the approved section hierarchy styles.
- Sections have at most two levels, with collapse arrows in headings. Distinguish first-level group headings from second-level light-background content areas without tree lines. Items have no parent/child relationships; check circles are always left-aligned and second-level name content is indented 16px.
- Internal Template sections (Section) have at most two levels, excluding the root container and Items. Sections are independent of flat Categories and category-source groups. The server prohibits cycles, cross-document links, and subtree moves exceeding the depth limit.
- Each entry has only one section position. Adding the same Item across sections still automatically merges and retains its existing position; explicit moves do not change Item identity or checked state. Sections are not sources and have no checked state.
- Template saves current section structure; instantiating a Checklist copies sections for independent editing under the same two-level limit. Copy/archive/restore/convert-to-template preserve the structure. Existing content defaults to the root container; history is not rewritten.
- Deleting a nonempty section promotes its contents to the parent by default, preserving relative order without implicitly deleting entries. Implement sections through shared Documents and Modal, with API validation and historical snapshots synchronized.

- Database schema is defined solely by version 1 in `server/db.ts`, recorded in `PRAGMA user_version` (STRICT tables, CHECK constraints, foreign-key indexes). New databases create tables directly; other versions refuse startup. Retain no old-version upgrade or compatibility code. **Database version upgrades (any change to table structure, constraints, or user_version) must be clearly explained to the user beforehand and receive consent; do not bundle them with feature changes.** Prefer database-enforced constraints: A partial unique index ensures Item uniqueness per document, and sections use the `sections` table (documentId cascading, deferred parentSectionId/sectionId foreign keys, afterEntryId: NULL=after sibling entries, empty string=first). Category member order is item_categories.position (NOT NULL; append new members). Category has no parentId. There are no category-source tables (groups/entry_sources/entries.direct) or template_revisions; Template stores only current content. Archive snapshots use schemaVersion 2; do not read other versions. On 2026-10-13, with user consent, tables were deleted directly within version 1 without increasing user_version; old databases are incompatible and development data is rebuilt.

- The server reads global configuration from data/loom.config.json at startup (LOOM_CONFIG can specify a path), with auth.enabled defaulting to true. Missing custom files, invalid JSON/types, and unknown fields must fail startup; a missing default file still enables authentication. Configuration changes require restart; the frontend must not decide whether to bypass authentication using local flags.
- Authentication-disabled mode does not require account initialization. /session returns authEnabled:false and process-level CSRF; the root opens /checklists, direct links are preserved, and sign-out is hidden. Authenticated mode still defaults to /items, with unchanged session and password-manager behavior. Re-enabling authentication protects the same database without deleting accounts/data.

- Item itemGroup is an independent catalog-filter field: Each Item has at most one group name (at most 200 characters, trimmed; blank/null means Ungrouped). It does not change Category, sections, category sources, or history. Editing reuses ResourceDialog, and tabs reuse shared Button styles with keyboard support. Search intersects with group filtering; creation within a group defaults to that group. Omitting the field in API PUT preserves its old value; null clears it.
- ResourceDialog field labels uniformly use 13px/18px with 16px field spacing. Categories use a borderless fieldset with a left-aligned legend. Options are wrapping tag blocks with native checkboxes and text centered, and mobile click targets of at least 44px. Do not restore the misaligned legend outer-border layout.
- Group filter entry points are rounded tags, wrapping on desktop and scrolling horizontally in a single row on mobile. Item cards and list rows use the shared SortableRow to drag onto group tags and replace their single group; Ungrouped clears it, and All is not a drop target. Retain mobile long press and mouse thresholds, target highlighting, suppression of opening after dragging, version validation, and preservation on failure. Keyboard users can still set Group through the Item editing dialog.
- Shared SortableRow must provide visible drag feedback: A floating name preview follows the pointer, the original entry fades as a placeholder, and targets highlight. On mobile, show it immediately on long press. The preview must not intercept pointers or duplicate interactive DOM. Clean up on release/cancel/Escape/unmount and respect reduced-motion.
- Item cards and list rows both show Group tags (including Ungrouped), sharing the metadata layout with Category. Refresh after a successful drag and keep cards equal in height.
- Cards/list rows have no mouse-selection outline. Hover transitions smoothly, and keyboard focus is drawn inward to avoid clipping. Item route details are editing dialogs and must preserve the background catalog search bar, query, and Group; changes to route.id must not hide or clear search.
- Editable Group selectors share web/combobox.tsx; do not use native datalist popups with uncontrollable styles. Dropdowns match the field width, reuse the theme and common buttons, and retain arrow-key/Enter navigation, layered Escape closing, new-name and Ungrouped input, and disabled fieldset semantics.
- Group drop-target tags must remain reachable in long lists: The group bar sticks to the top, wraps with a limited height on desktop, and scrolls horizontally in one row on mobile. Show fades at left/right only when that side still has hidden tags. Keyboard selection of tags automatically scrolls them into view. Active keyboard Combobox options automatically scroll into view, and initial up/down keys correctly select the last/first option. Cover long lists, 25 groups, fast mouse movement, and touch regressions.

- Inline and card-corner actions prioritize the shared Button icon style and Icon, with required aria-label/title. Larger primary actions use icon plus text. Removing category members only unlinks the relationship, using a remove icon without implying Item deletion.
